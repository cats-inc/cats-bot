# Service Registry

> Every listener this project opens, so port conflicts are visible before they
> happen. Keep this current when a listener or its configuration changes.

## Services

This repository registers no fixed port. Each running bot owns its loopback
listeners, whose ports are chosen by the operating system at startup:

| Service Name | Port | Protocol | Description | Start Command |
|--------------|------|----------|-------------|---------------|
| cats-runtime (app-managed child) | dynamic (a free loopback port reserved by the core at each start) | HTTP | The bot's private `@cats-inc/cats-runtime` instance; the bot core reads the bound port from the `runtime.ready` stdout event and confirms it with `GET /health` | spawned by the bot core (SPEC-001 FR-5); never started by hand |
| bot tool server (PLAN-001 Phase 2) | dynamic (loopback only) | HTTP (MCP Streamable HTTP) | The bot's session MCP server (`schedule_create`, `schedule_list`, `schedule_cancel`, `ask_owner`), handed to the provider CLI through the runtime's `mcpServers` field | spawned in-process by the bot core |
| desktop control server (PLAN-006 P2) | dynamic (loopback only) | HTTP (MCP Streamable HTTP) | The `cats-desktop` session MCP (SPEC-006), beside the bot tool server. It opens with the first conversation that qualifies (BDC-04: Windows, helper present and answering, both switches on, an explicit interactive-approval policy) and is handed to the provider CLI only for such conversations. Each conversation gets its own bearer token, revoked when desktop control is switched off or the session changes; tokens are never logged | spawned in-process by the bot core |
| desktop control helper (PLAN-006 P2) | none | JSON lines over stdio | `cats-desktop-control-windows.exe`, started on first use, ended after 5 idle minutes or when desktop control is turned off; no listener | spawned by the bot core on Windows only |
| owner control (PLAN-004) | none | HTTP over random Windows named pipe / Unix socket | Authenticated local `interactions`, `respond`, and `capabilities`; descriptor contains only this host's token, never the Runtime key. Request bodies are bounded and never logged or handed off on disk. Unix socket/descriptor are owner-only; Windows uses the current account's pipe and profile access. | started and stopped by BotCore under its instance lock |
| host channel (PLAN-009 1.1) | none | newline-delimited JSON over random Windows named pipe / Unix socket | SPEC-008 FR-12 to FR-15: the presenting host (the hub) sends the commands of `src/core/host-api/commands.ts` and receives numbered events; the core asks the host for its secret cipher. Descriptor `host-channel.json` in the bot root holds the protocol, socket, per-start token, PID and manager; a hello with the token and protocol comes first, frames are bounded to 16 MiB and never logged | started and stopped by BotCore beside owner control |
| hub control (PLAN-009 2.5) | none | HTTP over random Windows named pipe / Unix socket | SPEC-008 FR-25: owner CLI hub commands (`cats-bot hub status`) reach the running hub. Descriptor `hub-control.json` in the Cats Bot root holds the socket, per-start token, PID and installation id, with owner control's account rules. Only deliberate refusals carry a reason; without a running hub the commands refuse | started and stopped by the hub |

The HTTP listeners bind `127.0.0.1` only, carry random bearer tokens, and
are never reachable from the shell's renderer (SPEC-001 FR-32).

## Environment Variables

| Variable | Default | Service | Notes |
|----------|---------|---------|-------|
| `CATS_BOT_HOME` | `~/.catsbot` | bot core | The Cats Bot root (SPEC-007 FR-3, FR-4): each bot data root is `<CATS_BOT_HOME>/bots/<bot-id>/` (SPEC-001 FR-2), and the rest is reserved for hub files (SPEC-008); tests always use a temporary root |
| `CATS_RUNTIME_DIR` | `<bot data root>/runtime` | cats-runtime child | Set by the bot core on the child; never inherited from the user's shell |
| `CATS_RUNTIME_API_KEY` | random per start | cats-runtime child | Generated by the bot core; never written to logs |
| `CATS_RUNTIME_NATIVE_DISCOVERY_INTERVAL_MS` | `0` | cats-runtime child | Disables the runtime's background native and agent session discovery (ADR-001 §1) |
| `CATS_RUNTIME_WSL_DISCOVERY_POLICY`, `CATS_RUNTIME_DOCKER_DISCOVERY_POLICY` | `manual_only` | cats-runtime child | Same reason |

The runtime's own `CATS_RUNTIME_HOST` / `CATS_RUNTIME_PORT` are not used: the
bot passes `--host 127.0.0.1 --port <port>` on the command line, where the port
was just reserved by binding and closing a loopback listener (cats-runtime 0.6.1
rejects `--port 0`).

## Running Beside Cats Desktop

A bot and Cats Desktop run side by side without port conflicts (checked on
2026-10-28 with both running on the same Windows machine):

- Cats Desktop listens on fixed loopback ports, 8181 for the app and 3110 for
  its runtime (`cats-platform/desktop/host/config.ts`, overridable with
  `CATS_DESKTOP_APP_PORT` / `CATS_DESKTOP_RUNTIME_PORT`).
- A bot asks the operating system for a free port (bind to port 0) for its
  runtime and its tool servers, so it only ever gets ports from the dynamic
  range (49152-65535 on Windows), never 3110 or 8181. The only overlap would
  come from configuring Cats Desktop onto a port inside that range.
- The runtime port is reserved and released just before the runtime binds
  it. If another program takes it in that moment, the runtime fails to
  start and the core retries with backoff and a newly reserved port
  (SPEC-001 FR-6).
- Every inherited `CATS_RUNTIME_*` variable, including `CATS_RUNTIME_PORT`, is
  dropped before the bot's runtime starts, so a value meant for Cats Desktop
  never redirects it.
- The bot's runtime keeps its own data directory (`<bot data root>/runtime`),
  so its session registry is separate from Cats Desktop's. This is not full
  isolation: only the background discovery (native and agent scans, WSL and
  Docker) is off. The runtime still watches the provider CLIs' own session
  folders (for example Claude Code's `~/.claude/projects`), which it also
  reads for `history` and resume, so sessions started elsewhere, Cats
  Desktop's included, can show up in the bot runtime's registry as
  `origin: 'discovered'`. The bot never takes them over: it never lists the
  runtime's sessions and knows its own only from its attachment records
  (ADR-001 §1). Both use the same provider CLI sign-in, by design.

## Cross-Project Port Coordination

This project was created from **project-bootstrap**, which maintains a central
port registry at `<bootstrap-project>/docs/port-registry.md`. Because every
listener here is dynamic and loopback-only, there is nothing to register there.
If a fixed port is ever introduced, add it to the table above and to that
registry, and warn about conflicts.
