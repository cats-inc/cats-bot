# Cats Bot 0.4.8 — Standard Preview

This compatible 0.4 patch makes in-app updates work again on Linux after Cats Bot has
restarted itself.

## Changes

- **Linux updates no longer fail with "The package manager exited 127"** (#105). Electron's
  `app.relaunch()` sets `NoNewPrivs` on the process it starts. Under that flag `pkexec`
  cannot gain root and exits 127 before any password prompt, so a copy started by that
  relaunch could not install its next update, and the restart after the failure kept
  the flag. Every Linux relaunch now keeps the host's existing state instead of adding
  the flag. Windows and macOS are unchanged.
- **A session that cannot update says so first** (#105). The flag is inherited and cannot
  be cleared, and Cats Bot does not bypass it. A copy already running with it now refuses
  before downloading or stopping any bot, and asks you to quit from the tray and open
  Cats Bot again from the applications menu.
- **Clearer installer errors** (#105). A closed password prompt and a failure to get
  administrator rights are reported separately, with `pkexec`'s own message. The last
  install's error output stays in `logs/update-install.log` in Cats Bot's Electron
  preferences directory.
- **A failed restart no longer strands the hub** (#105). If the replacement cannot be
  started, this is logged and Cats Bot still quits, rather than staying open with its bots
  stopped.

## Updating to this version on Linux

Installed 0.4.6 and 0.4.7 still have the bug, so a copy of either that was restarted by an
update or by a failed one cannot install this version from the tray:

1. Choose Quit from the tray.
2. Open Cats Bot from the applications menu.
3. Use Check for Updates… and enter the administrator password when asked.

A copy updated this way is started by the old version's relaunch, so it runs with the flag
until its next quit and reopen, or its next start at sign-in. If you update again before
then, the new message above tells you what to do.

## Downloads, signing and updates

- Windows x64/ARM64: `Cats-Bot-0.4.8-setup-<arch>.exe` and
  `Cats-Bot-0.4.8-portable-<arch>.exe`; updater `latest.yml`.
- macOS Universal (Intel x64 + Apple Silicon ARM64):
  `Cats-Bot-0.4.8-universal.dmg`, updater ZIP and `latest-mac.yml`.
- Debian/Ubuntu amd64/ARM64: `Cats-Bot-0.4.8-<arch>.deb`, with architecture-specific
  updater metadata.
- Per-platform receipts, `SHA256SUMS`, `Cats-Bot-v0.4.8-source.zip` and
  `Cats-Bot-v0.4.8-sources.json` accompany the installers.

Standard-profile expected trust: macOS **signed and notarized**, Windows
**unsigned: no certificate** (including the desktop-control helper), Linux
**n/a**. Receipts record actual trust and configured signature/notarization gates
enforce it. No unsigned override is selected.

Existing 0.4.x Windows NSIS and signed macOS installs using the same Developer ID
team retain their Check for Updates path. Linux uses the package manager.
Portable and unsigned Mac installations use manual replacement. There is no
automatic background installation. GitHub immutable releases and the active
`v*` tag protection remain enabled; publication attaches all assets before locking.

## Compatibility, backup and recovery

- Profile schema 2, hub/shell state, conversations and CLI/HTTP APIs keep their formats.
  No data migration or session reset is introduced.
- Before changing installations, stop Cats Bot and retain a copy of its data
  root (`~/.catsbot`, or the configured `CATS_BOT_HOME`) and Electron preferences.
  If installation fails, keep those directories intact and reinstall 0.4.8.
- The 0.4.7 installer reads the same data without conversion. Rolling back restores the
  relaunch that adds the flag, and leaves `logs/update-install.log` unused.

## Exact inputs and validation boundary

- **Bot:** version 0.4.8 from the merged bump commit selected for manual dispatch.
  After CI passes on that exact `main` commit, dispatch `bot-preview.yml` with
  `tag=v0.4.8`. The workflow creates the tag at publication; do not push it first.
  It verifies packaged identities, complete source/assets and checksums before
  publishing the Standard Preview with `make_latest=false`.
- **Runtime:** 0.6.2, source
  `fb0f1125ecad427852f0c890b36605f335945650`, unchanged from 0.4.7. Artifact
  `vendor/cats-runtime-0.6.2-fb0f1125.tgz`, SHA-256
  `8e20c1f65a636a2769fbc4e826828df3b2fdec6dcaf2497e326fc37607f3ce4c`.
- **Shared conversation UI:** `@cats-inc/platform-ui-web` 0.1.0, artifact
  `vendor/platform-ui-web-0.1.0-957e4717942c.tgz`, SHA-256
  `363e784f2d0571522006797b01772be55384ecec4ae0bccb254eabd7b6783501`.
- **Setup helpers:** Platform source
  `7b3f94ef822860f1ceb34398d93d8245f8fd39d0`, with all 35 per-file hashes in
  `assets/setup/provenance.json`, unchanged from 0.4.7. Other shared tooling remains
  pinned by `scripts/shared-tools.provenance.json`.
- **Existing evidence:** on installed 0.4.6 on a Raspberry Pi 5, the hub had `NoNewPrivs=1`
  and no `pkexec` or polkit record of the attempt, and `pkexec` under that flag printed
  `pkexec must be setuid root` and exited 127. A minimal Electron 41.2.0 app reproduced the
  flag appearing across `app.relaunch()`. #105 passed hosted CI on Linux, Windows and macOS
  and independent review, with its findings addressed. Real Electron 41.2.0 relaunches kept
  `NoNewPrivs` 0 to 0 and 1 to 1 headlessly on Ubuntu CI and on the Raspberry Pi 5 desktop,
  where the switch to X11 also kept 0 to 0. Restoring the native relaunch, replacing the wait
  for the old process with a delay, and removing the refusal's wiring each fail the tests.
- **Acceptance boundary:** these checks do not establish a real `pkexec` and `apt-get`
  install, which needs the administrator password. They also do not establish an installed
  0.4.6-or-0.4.7-to-0.4.8 upgrade, an in-app update from 0.4.8 to a later version, or the
  refusal in an installed copy. The existing 120-second installer wait includes the time
  spent at the password prompt and is unchanged, so a long pause there could report an
  uncertain result. The bump's CI and release workflow enforce their own exact-source gates;
  their hosted records carry the outcomes.

Publication results: the `v0.4.8` GitHub Standard Preview, platform receipts and
its Actions run. Publication verification checks immutable status, tag source,
public asset hashes, update metadata and release attestation.
