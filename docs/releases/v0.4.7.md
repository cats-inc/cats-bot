# Cats Bot 0.4.7 — Standard Preview

This compatible 0.4 patch makes the Linux avatar click-through, closes its menus on
an outside click, turns Start at login on after a new install's first run, separates
the hub tray from each Cat's menu and adds native work tools for Muse, Grok and
Antigravity.

## Changes

- **Linux avatar without black areas or blocked clicks** (#101). The avatar no longer
  sets an X11 bounding shape, which left black outside it under software compositing
  and kept taking every click inside its window. It now sets only an X11 input shape
  for the cat, bubble and state indicators, so clicks elsewhere reach the windows
  behind it. If the X connection fails, this is logged and the avatar still draws
  correctly, but its whole window takes clicks. An explicit
  `--ozone-platform=wayland` has no input regions, and remains unsupported for floating
  windows. See [ADR-014](../decisions/014-set-linux-avatar-input-through-the-x11-input-shape.md).
- **Menus close on an outside click on Linux** (#101, #102). Under XWayland a click on a
  native Wayland window never reached the menu. A transparent window now takes that
  click while a Cat or note layer menu is open. The click that closes a menu does not
  also reach the window under it. The window goes with the menu or its owner, and after
  30 seconds, which also closes a menu left open that long. Windows and macOS menus are
  unchanged.
- **Start at login** (#101).
  - Installed Linux copies now offer it, through
    `$XDG_CONFIG_HOME/autostart/cats-bot.desktop` (normally under `~/.config`). That
    file decides the setting, so removing or disabling it outside the app turns the
    setting off at the next hub start and it is not registered again. A file of that name Cats Bot did not
    write is neither replaced nor removed.
  - A new install's first run turns it on once, on every platform. Development shells,
    portable copies, a Mac app outside Applications and a copy run with `CATS_BOT_HOME`
    stay off. **Existing installations keep their setting, including off.**
- **Separate tray and Cat menus** (#100). The tray is global with zero, one or several
  Cats: Cats Bot Settings, Start at login, Check for Updates…, Quit and Show floating
  cats, and clicking it opens Settings on Bots. Each Cat's menu holds only its
  conversations, heartbeat, visibility, settings and desktop-control Stop. The tray's
  Stop all desktop control reaches every presented Cat, including a hidden one.
- **Native work tools for Muse, Grok and Antigravity** (#99). Provider access can select
  Runtime's native transports and existing approval UI. Switching modes waits for the
  active turn, restarts Runtime and hands conversation history to the new session without
  replaying queued messages. Muse and Grok receive Cats session tools. Antigravity's local
  tools and approvals require Google's official ACP executable, and Cats MCP stays gated
  there until native credential persistence can be verified. Its official Linux ARM64
  build currently fails on hosts with 16 KiB memory pages. Boss Cat tool status now
  requires authenticated discovery for the current execution.

## Downloads, signing and updates

- Windows x64/ARM64: `Cats-Bot-0.4.7-setup-<arch>.exe` and
  `Cats-Bot-0.4.7-portable-<arch>.exe`; updater `latest.yml`.
- macOS Universal (Intel x64 + Apple Silicon ARM64):
  `Cats-Bot-0.4.7-universal.dmg`, updater ZIP and `latest-mac.yml`.
- Debian/Ubuntu amd64/ARM64: `Cats-Bot-0.4.7-<arch>.deb`, with architecture-specific
  updater metadata.
- Per-platform receipts, `SHA256SUMS`, `Cats-Bot-v0.4.7-source.zip` and
  `Cats-Bot-v0.4.7-sources.json` accompany the installers.

Standard-profile expected trust: macOS **signed and notarized**, Windows
**unsigned: no certificate** (including the desktop-control helper), Linux
**n/a**. Receipts record actual trust and configured signature/notarization gates
enforce it. No unsigned override is selected.

Existing 0.4.x Windows NSIS and signed macOS installs using the same Developer ID
team retain their Check for Updates path. Linux uses the package manager.
Portable and unsigned Mac installations use manual replacement. There is no
automatic background installation. GitHub immutable releases and the active
`v*` tag protection remain enabled; publication attaches all assets before locking.

## Compatibility, backup and recovery

- Profile schema 2, hub/shell state, conversations and CLI/HTTP APIs keep their formats.
  No data migration or session reset is introduced. Existing profiles retain their
  permissions until the owner opts in to native work tools.
- Before changing installations, stop Cats Bot and retain a copy of its data
  root (`~/.catsbot`, or the configured `CATS_BOT_HOME`) and Electron preferences.
  If installation fails, keep those directories intact and reinstall 0.4.7.
- The 0.4.6 installer reads the same data without conversion. Rolling back restores the
  previous Linux avatar and shared menu, and removes native work tools, so return those
  providers' access to its earlier setting first. A Linux autostart entry stays and keeps
  starting the app at sign-in until `cats-bot.desktop` is deleted, because 0.4.6 does not
  offer the setting. Removing the package leaves that entry in place too, but its `TryExec`
  then makes it do nothing.

  `7b3f94ef822860f1ceb34398d93d8245f8fd39d0`, with all 35 per-file hashes in

  pinned by `scripts/shared-tools.provenance.json`.
- **Existing evidence:**
  - #101 and #102: hosted CI passed on Linux, Windows and macOS, and independent review
    of each found no reproduced defect, with its notes addressed in #102.
    `scripts/linux/test-avatar-input.sh` passed in a private labwc, using real pointer
    clicks through the compositor over a native Wayland window and compositor pixels. A
    `--linux dir` package started as a fresh install wrote a valid autostart entry, set the
    setting on, and closed its real right-click menu on an outside click; with an isolated
    `CATS_BOT_HOME` it wrote no entry. A menu left open lost its transparent window and
    closed at the 30-second limit, and closing its owner removed the window.
  - Before #101's rebase, the built avatar code ran on a real labwc desktop on a Raspberry Pi 5
    under software compositing: it authenticated with the session's cookie, terminal text
    showed through the transparent area, and the menu painted 3 of 3 times.
  - #100 passed independent review and an isolated real Electron acceptance with two
    disposable Cats. #99 passed independent review and 7 packed Runtime integrations,
    with scripted Antigravity checks that do not establish native binary acceptance.
- **Acceptance boundary:** these checks do not establish real pointer clicks on a real
  desktop, a click on a panel closing a menu, starting from a real sign-in, whether the
  tray is ready by then, Linux behaviour on other compositors, or the first-run default
  and menus on installed Windows or macOS copies. With an X11 window under the avatar,
  clicks on the cat went to that window once in a test session; this is not understood.
  A synthetic press and release at almost the same time can close a menu as it opens (1
  of 50), while clicks held 0 to 400 ms stayed open 90 of 90 times. They also do not
  establish an installed 0.4.6-to-0.4.7 upgrade, or a menu callback that truly never runs,
  which was not reproduced. The first-run default skips an isolated `CATS_BOT_HOME`, but
  the manual toggle and Windows' existing re-registration do not. The bump's CI and release workflow enforce
  their own exact-source gates; their hosted records carry the outcomes.
